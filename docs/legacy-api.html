01O que é

Uma API REST de xadrez multiplayer assíncrono. Dois jogadores se conectam a uma partida identificada por um ID legível — algo como brave-crimson-knight-e4 — jogam alternando lances em notação SAN, e qualquer pessoa pode acompanhar em tempo real via Server-Sent Events, sem precisar estar logada.

Três decisões definem o desenho inteiro:

  1. O estado do tabuleiro mora no MongoDB, não em memória. Cada requisição recarrega a partida do banco. Não existe sessão, sala ou processo por jogo.
  2. O relógio é preguiçoso. Não há timer, cron nem worker: o tempo restante é recalculado a partir de Date.now() toda vez que a partida é lida.
  3. SSE serve só para notificar, nunca como fonte da verdade. O evento carrega o estado novo, mas o cliente sempre pode reconstruir tudo com um GET.

O ponto mais crítico da arquitetura antiga

O fork do chess.js não é preferência — é consequência. O schema persiste o objeto Chess inteiro no Mongo (@Prop({ type: Chess })) e o reidrata com new Chess(game.board), passando um objeto em vez de uma string FEN. O chess.js oficial não aceita isso. Ver §11.

Duplicação de providers

Dois serviços são declarados no providers de módulos que também importam o módulo dono deles. No Nest o provider local vence — então existem instâncias duplicadas:

ServiçoDonoRedeclarado emConsequência
UsersService UsersModule AuthModule, GamesModule Três instâncias. Inofensivo hoje porque é stateless — mas errado.
SSEService SSEModule GamesModule Dois EventEmitter distintos. Funciona por acidente: subscribe e emit são chamados no mesmo controller, que resolve para a instância local. Um segundo módulo emitindo pelo SSEModule falaria sozinho.

A correção é remover das listas de providers e depender só do exports dos módulos importados.

05Endpoints

Legenda: ○ público · ● exige JWT

/auth

RotaCorpoResposta
○ POST /auth/signup { username, password } { user, accessToken } + cookie jwt
○ POST /auth/signin { username, password } { accessToken } + cookie jwt
● POST /auth/signout — { message: "success" }, limpa o cookie

Validação de cadastro

  • username — 2 a 32 caracteres, alfanumérico mais _ e .; não pode começar nem terminar com _/., nem ter dois seguidos.
  • password — 8 a 128 caracteres, sem exigência de composição.
/^(?![_.])(?!.*[_.]{2})[a-zA-Z0-9._]+(?<![_.])$/

Username duplicado: o erro 11000 do Mongo vira 409 Conflict.

RotaResposta
●GET /users/me{ id, username }
●GET /usersidêntico — alias no mesmo handler

O alias existe porque /users ainda não lista usuários; a intenção registrada em comentário era manter só /users/me no contrato público.

/games

RotaPré-condiçãoEfeito
○GET /games/:id/sse—Abre o stream SSE da partida
○GET /games—Lista partidas com gameState == "A"
○GET /games/:id—Devolve a partida, ou 404
○GET /games/:id/movesestado W ou A{ game, moves } — lances legais
●POST /games—Cria a partida
●POST /games/:id/joinestado WPOcupa a vaga livre, vai para W

●POST /games/:id/resigné jogador · estado W/ADesiste
●POST /games/:id/drawé jogador · estado W/AOferece ou aceita empate
●DELETE /games/:id/drawé jogador · estado W/ARetira a própria oferta

Corpo de POST /games

{
  "pieces": "w",
  "timeControl": { "white": 600, "black": 600, "increment": 5 }
}
  • pieces — "w" ou "b", opcional. Omitido, a cor é sorteada.
  • white / black — 10 a 5400 segundos.
  • increment — 0 a 10 segundos.

Corpo de POST /games/:id/move

{ "move": "Nf3" }

Validado por regex SAN antes de chegar ao motor — cobre lances de peça e peão, capturas, promoção, en passant e roque:

/^([PNBRQK]?[a-h]?[1-8]?[xX-]?[a-h][1-8](=[NBRQ]| ?e\.p\.)?|^O-O(?:-O)?)[+#$]?$/
Não existe endpoint de aceitar empate

O empate é modelado como dois booleanos — drawOffer.white e drawOffer.black. Aceitar é simplesmente chamar POST /:id/draw também; quando os dois ficam true, a partida encerra empatada. O DELETE zera apenas a sua própria flag. É uma simplificação elegante que vale preservar.

Só quatro estados, mas nove transições distintas para F. Cada uma preenche status.aditionalInfo com uma frase legível e grava status.result e status.finishedAt.
Detalhe que vale entender

updateStatus() sempre reconsulta o tabuleiro antes de olhar o motivo pedido. Se a posição já é xeque-mate, o tipo solicitado é sobrescrito: 

const board = new Chess(game.board)
if (board.isCheckmate())                 type = 'checkMate';
else if (board.isInsufficientMaterial()) type = 'insufficientMaterial';
else if (board.isStalemate())            type = 'stalemate';
else if (board.isThreefoldRepetition())  type = 'threefoldRepetition';
else if (board.isDraw())                 type = '50-moveRule';
switch (type) { … }

É elegante para detecção automática de fim de jogo — mas significa que uma desistência numa posição já empatada por material insuficiente é registrada como empate, não como desistência.

08Relógio e SSE

Os dois mecanismos que mais valem a pena preservar na reescrita.

8.1 · Relógio preguiçoso

Não existe timer, setInterval, worker ou job. O tempo é derivado.

sequenceDiagram
  participant C as Cliente
  participant Ctl as GamesController
  participant S as GamesService
  participant DB as MongoDB

  C->>Ctl: GET /games/:id
  Ctl->>S: findOne(id)
  S->>DB: findOne resourceId
  DB-->>S: documento
  S->>S: clock(game, Date.now())
  Note over S: turnTime menos o tempo<br/>desde o último lance
  alt tempo esgotado
    S->>S: updateStatus('timedOut')<br/>zera o relógio de quem tem a vez
  else ainda há tempo
    S->>S: grava o tempo restante
  end
  S->>DB: game.save()
  S-->>Ctl: partida atualizada
  Ctl-->>C: 200 + JSON
Toda leitura é também uma escrita. O save() dentro de clock() é o preço do relógio sem timer — e a dívida descrita em §10.6.

timeControl.turnTime é o snapshot do relógio de quem tem a vez, tirado no instante do último lance. clock() subtrai daí o tempo decorrido; se o resultado for zero ou menos, quem estava na vez perde por tempo. E isso é descoberto na próxima leitura, seja de quem for.

O incremento Fischer é aplicado em updateTimeControl(), chamado dentro de move() antes de game.turn ser trocado — ou seja, game.turn ainda aponta para quem acabou de jogar: 

const timeSpent = increment - ((moves[1].timestamp - moves[0].timestamp) / 1000);
game.timeControl.white   = game.timeControl.turnTime + timeSpent;  // brancas jogaram
game.timeControl.turnTime = game.timeControl.black;                // agora é a vez das pretas
VantagemCusto
Stateless de verdade: escala horizontal sem coordenação e sobrevive a restart do processo. Um GET escreve no banco, e ninguém é notificado do timeout até alguém consultar.

8.2 · Server-Sent Events

O SSEService inteiro cabe em 19 linhas:

@Injectable()
export class SSEService {
  readonly emitter: EventEmitter;
  constructor() { this.emitter = new EventEmitter(); }

  subscribe(id: string) { return fromEvent(this.emitter, id); }

  async emit(id: string, data: Object) { return this.emitter.emit(id, { data }); }
}

O resourceId da partida é o nome do evento no EventEmitter. O @Sse() do Nest consome o Observable devolvido por fromEvent e serializa cada emissão como um evento SSE. 

sequenceDiagram
  participant W as Espectador
  participant B as Jogador das pretas
  participant Ctl as GamesController
  participant SSE as SSEService
  participant DB as MongoDB

  W->>Ctl: GET /games/:id/sse
  Ctl->>SSE: subscribe(resourceId)
  SSE-->>W: stream aberto (text/event-stream)

  B->>Ctl: POST /games/:id/move Nf3
  Ctl->>Ctl: verifyPlayer, verifyTurnPlayer, getGameStatus
  Ctl->>DB: aplica o lance e salva
  Ctl->>SSE: emit(resourceId, type move)
  SSE-->>W: data com a partida atualizada
  Ctl-->>B: 200 + partida
O espectador nunca autentica. O @Sse é a única rota de escrita adjacente sem guard — provavelmente intencional, mas nunca documentado.

Eventos emitidos

Sempre no formato { type, game }, com game já serializado:

typeDisparado por
joinPOST /:id/join
movePOST /:id/move
resignPOST /:id/resign
drawOfferPOST /:id/draw
drawCancelDELETE /:id/draw

Limites

  • Sem autenticação no @Sse — qualquer um assiste qualquer partida. Provavelmente intencional para espectadores, mas vale decidir conscientemente.
  • Em memória, por processo. Com mais de uma instância da API, um cliente conectado à instância A não recebe o lance processado pela instância B. Escalar horizontalmente exige Redis Pub/Sub ou equivalente.
  • Sem replay, heartbeat ou Last-Event-ID. Reconexão perde o que passou; a recuperação é refazer o GET /games/:id.
  • O relógio não gera evento. O fim por tempo só aparece quando alguém lê a partida — o espectador pode ficar olhando uma partida já encerrada.

Cookie primeiro, header depois. Aceitar as duas formas foi o que permitiu o mesmo backend servir navegador e cliente de linha de comando. 
jwtFromRequest: ExtractJwt.fromExtractors([(request: Request) => {
  const data = request?.cookies["jwt"];
  if (!data) {
    try { return request?.headers.authorization.replace('Bearer ',''); }
    catch { return null; }
  }
  return data;
}])

O validate() devolve { user: payload } — e é por isso que todos os controllers escrevem req.user['user'], um aninhamento estranho que se propagou por toda a base.

O payload do JWT tem só { id, username }. signout apenas limpa o cookie: o token continua válido pelos sete dias, e quem tiver guardado o accessToken segue autenticado. Não há blacklist nem refresh token.

10Bugs e dívidas

Levantamento feito na leitura do código, ordenado por gravidade. Serve de checklist do que não repetir na reescrita.

Bugs reais 5 itens
01
A verificação de partida inexistente no SSE nunca dispara
games.controller.ts:35 — falta o await
const game = this.gamesService.findOne(id)   // Promise, sempre truthy
if (!game) throw new HttpException('Game not found.', HttpStatus.NOT_FOUND);

GET /games/id-inexistente/sse abre um stream que nunca emite nada, em vez de devolver 404. É a única chamada a findOne sem await no arquivo.

02
O criador pode jogar sozinho contra si mesmo

getGameStatus(game, 'join') só confere se o estado é WP. Ninguém verifica se quem está entrando é o próprio criador — então ele ocupa as duas cores. A função wichPlayer() inclusive trata esse caso devolvendo 'wb', e drawRequest sabe empatar consigo mesmo. Pode ter sido intencional como modo treino, mas não está documentado em lugar nenhum.

03
O primeiro lance das brancas é grátis

Em updateTimeControl, quando o histórico tem só um lance a função apenas define turnTime = timeControl.black e retorna, sem debitar o tempo que as brancas levaram para jogar.

04
FEN inicial incompleto
games.schema.ts:5
'rnbqkbnr/pppppppp/8/8/8/8/PPPPPPPP/RNBQKBNR'
                          falta: ' w KQkq - 0 1'

É só o valor default do campo FEN — o tabuleiro real vem do objeto Chess — mas qualquer cliente que confie nesse FEN antes do primeiro lance recebe uma string inválida.

05
Mensagem de validação trocada
users.dto.ts:11

@MaxLength(32, { message: 'Username must be at least 32 characters long' }) — deveria ser at most.

Arquitetura 7 itens
06
GET escreve no banco

findOne() chama clock(), que chama game.save(). Toda leitura de partida é uma escrita. Além de violar a semântica de GET, multiplica a carga no Mongo e cria corrida quando vários clientes consultam ao mesmo tempo.

07
SSE não sobrevive a mais de uma instância

EventEmitter em memória — ver §8.2. Escala horizontal exige um broker.

08
Instâncias duplicadas de providers

Ver §2 — UsersService em triplicata, SSEService em duplicata.

09
Nenhuma proteção contra lances simultâneos

findOne → valida → save(), sem transação nem controle de concorrência otimista. Dois POST /move simultâneos podem ler o mesmo estado, e o último sobrescreve o primeiro.

10
Toda a lógica de negócio em funções soltas

wichPlayer, updateTimeControl, updateStatus, selectPieces e generateResourceId são funções módulo-privadas no fim de games.service.ts, fora da injeção de dependência e portanto intestáveis isoladamente. updateStatus é um switch de 85 linhas.

11
Validação repetida em todo handler

O padrão findOne → if (!game) 404 → getGameStatus → verifyPlayer se repete em seis dos nove handlers. É exatamente o caso de uso de um guard ou interceptor — que, aliás, é o que a reescrita já introduziu.

12
strictNullChecks e noImplicitAny desligados

O tsconfig.json desliga as duas verificações mais úteis do TypeScript. Daí vêm construções como verifyPlayer declarada Promise<boolean> mas com return null no caminho de erro.

Segurança 4 itens
13
signout não invalida nada

O JWT segue válido por sete dias — ver §9.

14

Nem em signin, nem em signup.

15

A camada utils — a mudança estrutural real

O legado repetia throw new HttpException(...) em cada handler e devolvia um formato diferente por rota. A reescrita move isso para três peças transversais registradas no main.ts:

PeçaResponsabilidade
GlobalExceptionFilter Captura tudo, normaliza para um envelope de erro e loga método, path, statusCode, mensagem e stack via Logger.
MongoExceptionFilter Traduz MongoError — hoje só o 11000 de chave duplicada.
GlobalResponseInterceptor Embrulha toda resposta de sucesso no mesmo envelope, lendo a mensagem do @WrapMessage via Reflector.

O @WrapMessage('User created') é o detalhe bem resolvido: o handler continua devolvendo só o dado, e a mensagem vira metadado do endpoint em vez de virar if dentro do controller.

14O que quebrou no caminho

A fundação é melhor, mas o código novo trouxe defeitos próprios. Dois deles são graves e se mascaram mutuamente — por isso nenhum apareceu em uso manual.

Crítico 2 itens · verificados em execução
01
Qualquer senha autentica qualquer usuário
users.service.ts:25 — falta o await
if (!this.comparePassword(userSignDto.password, user.password)) return null;
//  ↑ comparePassword é async: isto testa uma Promise, que é sempre truthy

!Promise é sempre false, então o return null nunca executa e checkPassword devolve o usuário independentemente da senha. Basta saber um username para entrar na conta.

É exatamente a mesma classe de erro do §10.1 do legado — um await faltando dentro de um if — só que agora no caminho de autenticação. Reproduzido isoladamente: com a comparação forçada a false, a função ainda devolve aceito.

02
O sub do JWT é undefined
user.schema.ts:8 — a prop id sombreia o virtual do Mongoose
@Prop({ type: String, readonly: true })
id: string;                       // nunca recebe valor

// auth.service.ts
const jwtPayload = { sub: user.id, username: user.username };

O Mongoose expõe um virtual id que devolve _id como string — a menos que o schema declare um path chamado id, e aí o path real vence. Testado com o schema atual: doc.id devolve undefined, enquanto o mesmo schema sem a prop devolve o _id corretamente.

Consequência: todo token emitido carrega sub: undefined. A correção é remover a prop e deixar o virtual trabalhar.

Por que nada disso apareceu

A JwtStrategy recebe o payload do token — { sub, username } — mas está tipada como UserSignDto e o repassa para checkPassword, onde password é undefined. E bcrypt.compare(undefined, hash) rejeita com “data and hash arguments required”.

Ou seja: o guard só não explode porque o bug nº 1 impede que o resultado seja aguardado. Consertar o await sozinho vai derrubar a validação do JWT. Os dois precisam ser corrigidos juntos — e a estratégia deveria confiar na assinatura do token, não reconsultar o banco e refazer bcrypt a cada requisição.

Arquitetura e configuração 5 itens
03
O JWT expira em 60 segundos
auth.module.ts:16 — signOptions: { expiresIn: '60s' }

O legado usava sete dias. Sessenta segundos tem cara de sobra de teste — inutilizável na prática, e sem refresh token para compensar.

04
Autenticação por Bearer apenas

ExtractJwt.fromAuthHeaderAsBearerToken() substituiu o extractor que tentava cookie e caía para header (§9). O cookie-parser está comentado como TODO no main.ts. Um cliente de navegador perdeu o caminho httpOnly.

05
Nenhuma rota é protegida

JwtAuthGuard existe em utils/guards/ mas @UseGuards não aparece em lugar nenhum da base. O caminho autenticado inteiro está, hoje, sem exercício.

06
CORS desapareceu

O legado tinha enableCors com CORS_ORIGIN e credentials: true. O main.ts atual não configura nada — a API só responde a mesma origem.

07
A checagem de duplicidade virou racy
if (await this.findOne(username))
  throw new ConflictException('User already exists');

O legado deixava o índice único do Mongo decidir e traduzia o erro 11000 — atômico e correto. A reescrita faz uma consulta antes, o que abre janela de corrida entre a leitura e a escrita, e ainda torna o MongoExceptionFilter quase inalcançável.

Some-se a isso que o filtro faz throw de dentro do catch(): exceções lançadas por um filter não reentram na cadeia de filters, então esse caminho escapa do envelope JSON padronizado. Vale confirmar em runtime quando houver como reproduzir a corrida.

15Caminho até a paridade

Na ordem em que eu atacaria — cada bloco desbloqueia o seguinte.

  1. Fechar o buraco de autenticação. O await em comparePassword e a prop id do schema, juntos, mais reescrever JwtStrategy.validate para confiar no payload assinado em vez de reconsultar o banco. Depois disso, expiresIn volta para algo utilizável.
  2. Provar o caminho autenticado. Trazer o /users/me de volta e pôr o JwtAuthGuard nele. É a menor rota possível que exercita guard, strategy, envelope e filtros de ponta a ponta.
  3. Escrever os primeiros testes. O legado morreu com zero cobertura e a reescrita está repetindo isso. Os dois bugs críticos acima morreriam num único teste de “senha errada deve falhar”. O test:e2e também está quebrado por configuração — falta moduleNameMapper para os imports src/….
  4. Ligar strictNullChecks. Com 484 linhas o custo é baixo; com o módulo de games escrito, será alto. É agora ou nunca.
  5. Decidir sobre o chess.js (§11.1) antes de escrever a primeira linha de games — a escolha define o schema inteiro.
  6. Portar games, depois sse. Com a Parte I como especificação: máquina de estados do §7, relógio do §8.1, eventos do §8.2, e as nove dívidas que voltam a valer segundo o §13.
